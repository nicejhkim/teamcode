# 작업 루프

`/work`가 코드를 고치기 전에 읽는다. 매 세션에 넣지 않는다.
프로젝트에서 뒤집히면 안 되는 결정은 `AGENTS.md`에 있다. 이 문서는 스택과 상관없이 같은 작업 순서다.

검사 명령(`yarn`, `pytest` 등)은 여기에 적지 않는다. 그 저장소에 이미 있는 검사만 실행한다.

## 불변 제약

1. **읽기 우선.** 수정 전에 대상과 비슷한 구현을 읽는다. 기억으로 코드를 짐작하지 않는다.
2. **패턴 준수.** 그 자리에 있는 기존 코드의 구조와 이름을 따른다. 기존 코드가 나빠 보여도 그 자리에서 임의로 고치지 않는다. 새로 쓰는 코드는 프로젝트 규칙을 따른다. 기존 문제를 발견하면 알리고, 고칠지는 확인받는다.
3. **정책 보존.** 조건, 계산, 권한처럼 동작의 의미를 요청 없이 바꾸지 않는다.
4. **최소 변경.** 요청받은 것만 수정한다.
5. **범위 준수.** `AGENTS.md`의 불변 규칙, 열린 게이트, 보호 경로를 어기지 않는다. 작업이 이와 충돌하면 구현을 멈추고, PRD를 먼저 고쳐야 한다고 알린다. 작업 방식 자체를 바꿔야 하면 [workflow-log.md](workflow-log.md)를 따른다.

## 루프

```
GROUND → APPLY → VERIFY
  ↑                 ↓
  └─── ADAPT ←──────┘
       (실패할 때만)
```

### GROUND

대상 범위를 확인하고, 고칠 파일과 비슷한 구현을 읽는다. 그 결과로 규모를 정한다.

| 규모 | 기준 | 행동 |
|---|---|---|
| **S** | 파일 하나, 수정이 분명하다 | 바로 APPLY |
| **M** | 파일 2~5개, 기존 패턴을 따른다 | 따를 패턴을 한 줄로 정한 뒤 APPLY |
| **L** | 파일 6개 이상이거나 새 구조다 | 계획을 보여주고 확인받기 전에 APPLY 하지 않는다 |

버그를 고칠 때, 의도가 코드·테스트·이름에 보이면 그대로 진행한다. 의도를 읽을 수 없으면 묻는다. M 이상이면 해결을 2~3개 보여주고 고르게 한다.

동작을 유지한 채 구조를 바꿀 때는, 그 동작이 아직 맞는지 확인할 검사를 먼저 둔다.

### APPLY

GROUND에서 본 패턴으로 구현한다. 불변 제약 다섯 가지 안에서만 고친다. 파일을 고치는 주체는 `work-implement`다. 계획을 세운 세션이 직접 고치지 않는다.

### VERIFY

도구로 확인한다. 통과 판정은 파일을 고치지 않는 `work-review`가 한다. 구현한 주체가 통과를 선언하지 않는다. 통과하면 끝이다.

- 수용 조건을 하나씩 확인하고, 각 조건에 근거를 붙인다.
- 저장소에 이미 있는 검사만 실행한다. 없는 검사는 만들지 않고, 없다고 보고한다.
- 호출처가 깨지지 않았는지 본다.
- diff가 요청한 범위만 포함하는지 본다.

### ADAPT

검증이 실패하거나, 사용자가 결과를 거부하면 들어온다. 거부는 의도를 다시 확인한 뒤에 들어온다.

1. **증상** — 무엇이 실패했는가
2. **원인** — 표면이 아닌 이유
3. **교정** — 이번과 다른 접근
4. 교정한 맥락으로 GROUND에 돌아간다

같은 원인으로 두 번 실패하면 세 번째 시도를 하지 않고, 증상과 원인을 보고한 뒤 멈춘다.
